The important architectural decision is this: do not use an in-memory Python lock as the correctness mechanism. It breaks as soon as you run multiple seller instances. PostgreSQL must be the single authority.
At a design level, I would use:
- A sale generation/ID so reset creates a fresh logical sale rather than relying on unsafe deletion during traffic.
- A ticket inventory table with exactly the configured ticket numbers.
- A purchase/idempotency record with a database-level unique constraint on request_id.
- A database transaction that atomically:
  1. returns the existing result for a repeated request ID,
  2. claims one still-available ticket,
  3. records the purchase,
  4. commits before replying.
- A status query derived from the same committed ticket/purchase data—not a separately maintained counter that can drift.
This directly protects the assignment’s four invariants. PostgreSQL serializable transactions are also an option, but they require retrying serialization failures; a carefully scoped row-lock/atomic-claim design is easier to explain and benchmark. PostgreSQL transaction isolation
Testing strategy:
- Unit tests: validation, sold-out response, repeat request ID.
- Integration tests against real Postgres: many simultaneous buyers, duplicate IDs racing concurrently, reset behavior, and status consistency.
- Property-style/concurrency tests: vary ticket counts, user counts, duplicate ratios, and request scheduling; assert all four invariants after every run.
- Required buyer: launch configurable concurrent HTTP requests, reuse a single HTTP client connection pool, deliberately replay IDs, fetch /status, and report pass/fail, RPS, median, and p99.
- Demonstration runs: naive implementation oversells; correct implementation passes; then increase load until p99 worsens and correlate that with PostgreSQL connection/lock metrics rather than guessing.
- Optional hard extension: run three FastAPI containers behind Nginx and one PostgreSQL container. The same tests should remain correct with zero shared Python locks.
I would choose Python 3.12, FastAPI, PostgreSQL, SQLAlchemy Core/psycopg, pytest/HTTPX/Testcontainers, and a custom asyncio buyer—plus Locust only for supplementary stress charts. It is small enough for the 12–15 hour limit, but it puts the interesting work exactly where the assignment evaluates it: proving database-backed correctness under contention.

The key design principle is: PostgreSQL, not Python, must be the authority that decides whether a ticket exists, is still available, and belongs to a request. That is what keeps the system correct across concurrent requests and multiple API instances.
Proposed database design
1. sales
Represents one fresh ticket sale created by /reset.
Column	Purpose
sale_id	Immutable ID for one sale generation
capacity	Requested ticket count, e.g. 100
created_at	Auditability
is_active	Identifies the current sale


Why it exists:
- /reset should create a new sale generation rather than deleting rows while requests may still be running.
- Every ticket and purchase belongs to one specific sale.
- It makes test runs and the required naive-vs-fixed demonstration easy to inspect.
2. tickets
Pre-create one row per ticket at reset.
Column	Purpose
sale_id	Which sale owns this ticket
ticket_number	Ticket number, from 1 through capacity
primary key: (sale_id, ticket_number)	Makes duplicate ticket numbers impossible within a sale


For a 100-ticket sale, /reset creates exactly ticket numbers 1–100.
Why it exists:
- The capacity is physical data, not merely an integer counter.
- /buy can only claim a row that already exists.
- Selling a 101st ticket becomes impossible because there is no ticket row to claim.
- A ticket number cannot be invented using unsafe logic such as “highest ticket number plus one.”
3. purchase_requests
Represents the durable result of an idempotent /buy request.
Column	Purpose
sale_id	Sale being purchased from
request_id	Client-generated idempotency key
user_id	Buyer identity
outcome	issued or sold_out
ticket_number	Set only when outcome is issued
created_at	Audit/debugging
unique: (sale_id, request_id)	One durable outcome per request
unique: (sale_id, ticket_number) where issued	One buyer/request per ticket
foreign key (sale_id, ticket_number) → tickets	Cannot issue a ticket that does not exist


Why it exists:
- A repeated request ID returns the already recorded result.
- The unique request constraint is the hard protection against two simultaneous copies of the same request buying two tickets.
- The unique ticket constraint is a second independent protection against assigning one ticket twice.
- Persisting sold_out is also useful: a retry of a request that was already told “sold out” receives the same answer.
A sensible rule is: if a reused request_id has a different user_id, reject it as invalid request-ID reuse rather than silently returning another user’s ticket.
What /buy should conceptually do
All of the following happens in one short database transaction:
request arrives
    ↓
Does this sale already have this request_id?
    ├─ Yes: return its recorded ticket / sold-out result
    └─ No:
         atomically claim one unissued ticket row
             ├─ ticket found: store “issued + ticket number”
             └─ no ticket: store “sold_out”
    ↓
commit transaction
    ↓
send response
The ticket claim uses database row locking, typically a “lock an available ticket row” operation. Other concurrent buyers cannot claim the same locked ticket. PostgreSQL constraints remain the final safety net even if application code has a defect.
Important: commit before replying. If the service says “you have ticket 42” before the transaction commits, then crashes, it may confirm a ticket that was never durably recorded.
How each invariant is enforced
Assignment invariant	Database-backed protection
Never sell more tickets than exist	Only pre-created inventory rows can be claimed
Never duplicate ticket numbers	Primary key on ticket inventory plus unique issued ticket assignment
Same request ID gets at most one ticket	Unique (sale_id, request_id)
/status count matches issued tickets	Derive both count and holder list from the same committed purchase/ticket records


For /status, do not maintain a separate sold_count value as the truth. Compute the count from issued purchase rows and produce the ticket-holder list from those same rows. Ideally, do it in one query or one read transaction so the count and list share one consistent database snapshot.
Why a simple /buy implementation fails
The tempting implementation is:
if sold_count < capacity:
    sold_count += 1
    assign ticket number sold_count
Under concurrency:
Request A reads sold_count = 99
Request B reads sold_count = 99

Request A decides ticket 100 is available
Request B decides ticket 100 is available

A writes 100
B writes 100
Possible outcomes:
- 101 tickets are reported sold.
- Ticket number 100 is assigned twice.
- A counter and the actual ticket list disagree.
- One write overwrites another, hiding the error.
A slightly less naive variant also fails:
if request_id does not exist:
    create purchase
Two duplicate requests can both check before either inserts:
Duplicate A: request ID not found
Duplicate B: request ID not found
Duplicate A: issues ticket 15
Duplicate B: issues ticket 16
Only a database unique constraint on the request ID prevents this reliably.
An in-memory Python Lock fixes the race only inside one process. It fails when:
- three FastAPI instances are behind a load balancer;
- a process restarts;
- deployment creates more workers;
- another script or admin job touches the database.
That is why the lock and constraints must be in PostgreSQL.
Reset design
/reset should create a new sales row and its exact ticket inventory atomically. Avoid “truncate everything” as the main model: an in-flight buy may otherwise start against data that disappears halfway through its transaction.
For the take-home’s normal sequential reset flow, switching the active sale after creating its inventory is enough. If we later want reset to be safe while buys are actively running, we should explicitly serialize reset against buying using a database-level coordination rule—not a Python mutex.
This design gives us a clean path to the three-instance extension: every FastAPI instance uses the same PostgreSQL constraints and transaction protocol, so no shared application lock is required.
